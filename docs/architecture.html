The shape of it

Two products, one protocol

The runner stack is the whole product. It clones, builds, signs, and ships on your own machines, and it works with nothing in front of it — a config file and a local trigger are enough. That part is open source, and it stays that way.

The hosted layer exists for one reason: you are not always at home, and your machines are not reachable from a hotel. It gives you a sign-in and a button. It does not give you compute.

Both halves speak the same protocol, so the hosted layer is swappable. Point the agent at your own deployment and nothing about the build changes. That is the deal Convex, Sentry, and Plausible offer, and it is the deal here.

The distinction worth stating plainly: the hosted tier is not rented runners. It is auth, a machine registry, a job queue, and the functions that move a job between them.

The runner stack

One binary — latem — and a config file per machine. Installs in a few minutes, runs as a service, survives reboots.

  • agentOutbound daemonHolds one connection to a queue. No ports to open, no dynamic DNS, works behind any NAT.
  • jobs.yamlLocal job registryNamed jobs, defined in your repo, on your disk. The only jobs that can ever run.
  • execExecutorsDocker on Linux, and two ways to do Xcode: the Mac's own OS by default, or an ephemeral Tart VM when the machine builds code you do not control.
  • cacheMounted cache volumesGradle, CocoaPods, DerivedData, pnpm and Cargo live in named volumes. No save step, no restore step, no size ceiling.
  • mobileExpo build pipelineLocal EAS builds wrapped in fastlane lanes, with match handling certificates from your own private repo.
  • triggerLocal triggerCLI, file watcher, or a git hook from your own Forgejo. No account required.

Hosted · the thin layer

Reach, from anywhere

A Convex backend and a small web app. Roughly a thousand lines of the thing, and none of it touches a build.

  • authAccountsSign in from a phone in an airport. Every machine belongs to exactly one owner.
  • machinesMachine registryPer-machine tokens, revocable individually, separate from your session.
  • queueRealtime job queueEach agent subscribes to rows matching its own machine id. Push, not poll.
  • hooksWebhook receiverAn endpoint your git host can call. Maps an event to a job name and enqueues it.
  • logsLog relay & historyWatch a build from a phone. See what ran last night and what it exited with.
  • alertsNotificationsPush when a build fails, and when a machine stops checking in.

Non-negotiable

Three rules that decide the blast radius

A control plane that can reach developer machines is a serious thing to operate. These are cheap to build in now and close to impossible to retrofit, so they are settled before the first commit.

Rule 01

The agent dials out

It opens the connection and subscribes to its own queue. The server never initiates anything.

Cost of getting it wrong: every user opens a port on their home network, and onboarding becomes a router tutorial.

Rule 02

Names travel, never definitions

The queue carries {repo, job}. The agent looks that up in a file it owns and refuses anything it doesn't recognise.

Cost of getting it wrong: a bug in one mutation becomes remote code execution on every machine ever registered.

Rule 03

Credentials stay home

Certificates, keystores and API keys live on the machine, encrypted in a repo you control. The backend never sees them.

Cost of getting it wrong: a breach costs users their App Store presence, not a failed build.

One job, start to finish

What actually happens when you tap Build

01PhoneYou pick a machine and a job name.Or a push to Forgejo hits the webhook and does it for you.
02Control planeA row lands in the queue.State queued, stamped with your account, the machine id, and the job name. That is the entire payload.
03AgentThe subscription fires.No polling delay. The agent claims the row, moving it to claimed, which also stops a second agent taking it.
04AgentThe name is resolved locally.Unknown name, or a job not allowed on this machine's labels, and it is rejected here — before anything executes.
05ExecutorA clean workspace comes up.A container on Linux; on a Mac, the host's own toolchain or a fresh Tart VM. Caches mount in; the workspace itself is disposable either way.
06ExecutorThe build runs.Your scripts, your toolchain. Logs stream out redacted, line by line, so a phone can watch a twenty-minute iOS build.
07ExecutorArtifacts land on your disk.Or go straight to TestFlight and Play from the machine that signed them. They do not route through the control plane.
08BothEnvironment torn down, result recorded.The row closes at passed or failed, a notification goes out, and the caches survive for the next run.

Order of work

Ship the runner first

The wedge is mobile. Free unlimited iOS and Android builds on a Mac you own is the thing people already want and can't easily assemble themselves — and it stands alone, with no backend at all.

First — prove the hard part

  • A local EAS build, run by hand on the Mac, once
  • Signing sorted end to end with match: certs, profiles, App Store Connect key
  • Android keystore and Play service account working from the desktop
  • CI logic pulled out into scripts, so no orchestrator owns it

Then — the open source release

  • Agent, job registry, and the three executors
  • Cache volumes, per-runner isolation, scheduled pruning
  • fastlane lanes for both platforms as documented defaults
  • Install script and a real quickstart. Works with no account.

Then — the thin layer

  • Convex schema: accounts, machines, jobs, logs
  • Machine tokens, subscription-based claiming, log relay
  • Web app: pick a machine, pick a job, watch it run
  • Later: labels and routing, artifact links, a guided path through Apple's credential setup

Two things to know going in. Self-hosted runners don't survive a GitHub Actions outage — the control plane schedules the work, so when it breaks, agents sit idle. Independence comes from your own git host and your own queue, not from owning the hardware. And push mirroring is one-directional and force-based: if GitHub is ever written to directly, the next local push overwrites it. Keep GitHub read-only and push through the tunnel instead.
