## What changed

**An agent can set a machine up** (RUNNER_SPEC A94). `latem setup --json`
has said for a while what stands in the way of each kind of build and how
each thing closes. Only the setup screen could close one, and the screen wants
a person at a terminal. `latem setup apply` closes them from a shell, as the
screen would:

```console
$ latem setup apply java-home android-home
java-home: wrote JAVA_HOME = /opt/homebrew/opt/openjdk@17/libexec/openjdk.jdk/Contents/Home; closed
android-home: wrote ANDROID_HOME = /Users/me/Library/Android/sdk; closed
now android is off, ready to turn on

$ latem setup apply --kind android
android: the check passed (the JDK compiles, the SDK's tools run), and the macos runner gains the label android; on
now android is ready
```

- An item's commands run as the screen runs them: each as an argv, with stdin
  closed and in a session of its own, so nothing can ask for a password.
  latem never runs sudo, accepts a licence or installs Xcode.
- An item's config.toml changes go through the same edit, and the same check
  that the file still loads, as every other command that writes it. Then the
  running agent is reloaded, or restarted at its next idle moment when only a
  restart applies the change.
- `--kind K` closes every item of K and then switches K on. Its label goes on
  its runner only once its check passes in the environment a step gets.
  Beside ids, `--kind K` only says to find them in K.
- What is yours stays yours, and says so with exit `4` and the lines you would
  type: commands with sudo, a licence, a secret's value, a runner's labels,
  and the two settings that give something up (`allow_unisolated` and
  `require_pinned = false`). Away from a terminal, apply refuses those two
  settings. At a terminal it asks first, defaulting to no.
- `--json` prints the plan afterwards, in exactly the shape `setup --json`
  prints.

Each command is one an agent's harness shows you before it runs. latem.dev's
MCP server has a skill, `set-up-a-machine`, that walks an agent through a new
machine with it, from installing latem to the first build.

**`latem mcp` says what a machine can build** (A95). Its new tool,
`getReadiness`, is `latem setup --json`, read-only. Pass `repo` to see only one
repository's kinds. It applies nothing: closing an item stays a command in a
shell on the machine, and `latem mcp` still offers no setup, service, secrets
or approval.

**A nested command's usage hint names it whole.** A wrong flag to
`latem setup android-sdk` pointed at `latem android-sdk --help`, which does not
exist.

### Upgrading from v0.9.1

- **Installed with `install.sh`:** run `latem update` once.
- **Installed with Homebrew:** run `brew upgrade latem`.

Either way, the running agent moves onto the new version at the first moment
no build is in flight.

Nothing changes until you run the new command. The wire protocol is still
2.9, and v0.10.0 leaves `state.db` and `config.toml` as v0.9.1 left them.
