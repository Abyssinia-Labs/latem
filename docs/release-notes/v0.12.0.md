## What changed

**A step after a failed step no longer runs because its `if:` was true** (RUNNER_SPEC A99).
This is the change to read first. On GitHub, a step's `if:` that calls no status
function (`success()`, `failure()`, `cancelled()`, `always()`) means
`success() && (if)`. Before this release, latem ran such a step whenever its own
condition held, even after an earlier step had failed. A workflow that tested and
then deployed behind `if: steps.changed.outputs.x == 'true'` deployed code that
had failed its tests. Now, once a step has failed or the run is cancelled, that
step is skipped, as on GitHub. Steps whose condition calls `always()` or
`failure()` still run, and a step forgiven by `continue-on-error` still leaves
the job's status `success`.

**Docker jobs on Kiri no longer fail at their first step** (A105). About 1 Linux
job in 10 failed in 0 s with `stat /bin/sh: no such file or directory`, because
the engine took an exec before its container was ready. The executor now waits
until the container is running and takes one exec. If it never does, the job
fails with `E_EXECUTOR` saying so, not as the step's failure.

**Setting up a new machine:**
- `latem setup --like <machine>` copies another machine's `[actions] allowed`
  and `[label_aliases]`, and asks once, at a terminal, for `allow_unisolated`
  and `require_pinned` (A102).
- A job whose `runs-on` names a label no runner here carries is now a readiness
  item. It names the alias that would route the job here, so a kind no longer
  looks ready while none of its jobs can reach the machine (A101).
- Label aliases are now the person's to agree to at a terminal.
  `latem workflows check --fix` shows each one and asks, and refuses off a
  terminal (A100).
- A kind with no label of its own, such as macOS apps, names the labels that
  turn it on, instead of staying off with no step to take (A107).
- Plan and doctor flag Xcode installed while `xcode-select` still points at the
  Command Line Tools (A108).
- Readiness now asks the Docker daemon the agent itself uses (`DOCKER_HOST`,
  else the system socket), not the `docker` command's context. It names the fix
  for Kiri, OrbStack, Colima or Rancher Desktop, and Docker Desktop's
  `com.docker.socket` helper when that is what took the socket back (A106).
- `latem setup` says one line per repository, so the connect code is no longer
  buried under per-job reports.

**OpenVault is becoming latem vault** (A104). latem now finds the vault as
`latem-vault` or `openvault`. It looks on `PATH`, in cargo's bin and in
Homebrew's. It reads it from `~/.latem-vault` or `~/.openvault`. This release
has to be on a machine before that machine's vault is renamed.

## Upgrading from v0.11

- **Installed with `install.sh`:** run `latem update` once.
- **Installed with Homebrew:** run `brew upgrade latem`.

Either way, the running agent moves onto the new version at the first moment no
build is in flight.

**Check your workflows if a step after a failure was meant to run.** If one
relied on the old behaviour, give it `if: always() && (…)` or
`if: failure() && (…)`. Almost every workflow was written for GitHub's rule and
needs nothing.

**Renamed, with the old names still accepted for one release:**
- `[secrets] openvault = true` becomes `[secrets] vault = true`. Both work.
- The readiness items `openvault-on`, `openvault-service`, `openvault-join` and
  `openvault-collection-…` are now `vault-…`. `setup apply` takes the old ids.
- The doctor checks `openvault.*` are now `vault.*`.
- The store is called `vault` in `latem secrets list`, `latem vars list` and a
  run's provenance.

An agent or script that matches these ids should accept both.

**Label aliases you already have stay as they are.** Only new ones ask.
