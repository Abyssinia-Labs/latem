## What changed

**A secret can be a file in OpenVault, and a step reads it as a path**
(RUNNER_SPEC A88). OpenVault 0.4 keeps files, such as a signing keystore, an
App Store Connect `.p8` or a service account's JSON, encrypted and synced like
any entry. Until now a keystore travelled as `ANDROID_KEYSTORE_B64`, and every
job's script decoded it into a temporary directory. Now the file can be the
secret itself:

```sh
openvault import upload.jks --collection app --into production
```

```yaml
    environment: production
    steps:
      - run: ./gradlew bundleRelease -Pandroid.injected.signing.store.file="$UPLOAD_JKS"
        env:
          UPLOAD_JKS: ${{ secrets.UPLOAD_JKS }}
```

- A name that is no secret or variable in a scope is looked up there as a
  file, by the name `openvault run` gives it: the last part of its name,
  upper-cased, with everything but A–Z and 0–9 turned into `_`. For
  environment `E` that is a file anywhere in folder `E`; for the repository,
  one at the top of its collection. A secret or variable of the same name
  comes first.
- The file is read as the job starts. Before the first step it is written
  into the job's temporary directory as `latem-secret-<file name>`, readable
  only by the job's user, and `${{ secrets.NAME }}` is that path, never the
  bytes. The copy goes with the job.
- Only a native runner gets files. A docker job that reads one fails before
  it starts, with `E_MISSING_SECRET`, because a docker job's temporary files
  can be read by every user in its container.
- A file over 16 MiB, two files that would set one name, or chunks no device
  has fail the job rather than read as unset.

**A collection that holds a file can be listed again.** Since OpenVault 0.4 a
listing carries a file's size and missing chunks, and v0.7.0 read the next
entry from the middle of them. One file in a collection failed
`latem secrets list`, `latem workflows check` and the readiness the heartbeat
sends latem.dev, with "a listing that does not parse". `latem secrets list`
now shows a file by the name a workflow reads it as.

**`latem mcp` is reached by its path.** The line v0.7.0's notes gave,
`ssh mini latem mcp`, fails with `command not found`: ssh runs a command with
a short `PATH`, which has neither `~/.local/bin`, where `install.sh` puts
latem, nor Homebrew's bin. Name the path instead:

```sh
claude mcp add --scope user mini -- ssh mini .local/bin/latem mcp
```

With Homebrew on a Mac with Apple silicon, it is `/opt/homebrew/bin/latem`.
`latem mcp --help` on the build machine now prints the line with its own
path, ready to copy. If you added a server with the old line, remove it with
`claude mcp remove --scope user mini` and add it again.

### Upgrading from v0.7.0

- **Installed with `install.sh`:** run `latem update` once.
- **Installed with Homebrew:** run `brew upgrade latem`.

Either way, the running agent moves onto the new version at the first moment
no build is in flight.

**A machine whose collections hold no files builds as it did.** A file is
looked up only for a name that has no secret or variable in that scope.

**Keep the values `latem store check` and `latem doctor` read.** They still
read the Android keystore, the Play service account and the `.p8` as values,
`ANDROID_KEYSTORE_B64` and the rest of RUNNER_SPEC §18, so a repository that
moves them to files keeps those values until the two commands learn files
too.

**The wire protocol is still 2.9**, so latem.dev and machines on v0.7.0 are
unaffected, and v0.8.0 leaves `state.db` as v0.7.0 left it.
