## What changed

**A job can keep its workspace between runs** (RUNNER_SPEC A90). Until now
every run of a `.latem/jobs.yaml` job built in a new clone, so its compiler
started from nothing each time. A job that says `workspace: warm` builds in a
directory the machine keeps for it:

```yaml
jobs:
  test:
    runs_on: [macos]
    workspace: warm         # fresh, a new clone per run, unless you say so
    steps:
      - name: test
        run: cargo test
```

- Every run starts with each tracked file at its commit, compared by content.
  Only the files that differ are written, so a build tool that goes by
  modification time rebuilds only what changed.
- What the repository ignores (`target/`, `node_modules/`) is still there. A
  file that is neither tracked nor ignored is removed.
- The directory is the job's own on that runner,
  `~/.latem/warm/<repo>/<runner>/<job>/tree`, at the same path every run, and
  runs of the job take turns on it.
- A warm workspace is a build's whole output, and takes that much disk. One no
  run has used for 7 days (`agent.warm_retention`) is removed. `latem cache ls`
  lists each with its size, and `latem cache prune` removes the unused ones.
- It is for `.latem/jobs.yaml` jobs, not a workflow's. A repository with
  submodules or git-lfs builds in a fresh clone, and the log says so.

On a Mac's native runner, a Rust workspace's `cargo test --no-run` took 12.6 s
in a new warm workspace and 3.9 s after a change to one file.

**A run can be a commit plus changed files, with nothing pushed** (A91). The
caller names a commit the machine's remote has, and sends each changed file
whole and the paths removed:

```json
{"base": "<40 hex>",
 "files": [{"path": "src/lib.rs", "text": "…"},
           {"path": "logo.png", "base64": "…"},
           {"path": "ci/test.sh", "text": "…", "mode": "755"}],
 "remove": ["src/old.rs"]}
```

```sh
latem run myapp test --changes changes.json     # or - for stdin
```

- The files become a commit on no ref in the machine's own mirror, a child of
  the base, and the run is pinned to it as `latem try` pins a working tree's.
  The same base and changes are always the same commit. Nothing about the run
  reaches latem.dev.
- The job reads the base as `$LATEM_BASE_SHA` and the changed paths, one to a
  line, from the file `$LATEM_CHANGED_FILES` names, so a test job can run what
  the change touches. With `workspace: warm`, only the changed files are
  written before the build starts.
- One set of changes is at most 5,000 paths and 16 MiB. Symlinks and
  submodules cannot be changed this way.

**An agent can send changes through `latem mcp`, where the machine says so.**
`startRun` takes the same JSON as `changes`, and refuses it unless the
repository has this line in that machine's `config.toml`:

```toml
[repos.myapp]
allowed_refs  = ["main"]
agent_changes = true
```

The base must be in the history of a ref `allowed_refs` admits, and the job
must be one the base's `.latem/jobs.yaml` declares, which the changes may not
touch. The agent can change every script and source file the job runs, and on
a native runner a step runs as you, so give the line for a repository whose
jobs you would let that agent run. Each refusal names the rule it broke.
`latem run --changes`, typed by a person, needs no line.

**Every run leaves what broke, by file and line** (A92):

```console
$ latem result r_a9ebf5ded6aac0b56fe40fbc
r_a9ebf5ded6aac0b56fe40fbc failed (E_STEP): step "test" exited 101
  job tier2 of anvers at 3b10592fa747, changes on cc276f84bc76, on macos, warm workspace, 1.8s

STEP  OUTCOME            TIME  ERRORS  WARNINGS
test  failure, exit 101  1.5s  1       0

1 error(s), 0 warning(s)
error crates/anvers-gate/tests/gate.rs:458:5  latem_e2e_fails  (cargo-test, step test)
    assertion `left == right` failed: the change broke arithmetic
      left: 2
     right: 3
```

- `--json` is the same result as one document: each step's outcome, exit code
  and duration, and each problem's severity, file, line, column, message, the
  tool's code (`E0308`, `TS2322`, a lint rule), the failing test's name, and
  the tool's own suggested fix when it printed one.
- It is read off the run's log, after the redactor, by readers for rustc and
  clippy, `cargo test`, go's compiler, vet and `go test`, tsc, `bun test`,
  vitest, biome, pytest, and anything that prints `file:line:col: error:` the
  way clang does. There are none yet for Gradle, jest or xcodebuild's test
  failures. A script names a problem itself with
  `echo "::error file=src/x.c,line=3::what is wrong"`.
- `latem mcp`'s `getRun` and `waitForRun` return the result with the run, so
  an agent no longer reads the end of a log to learn what failed. A client
  that sends a progress token with `waitForRun` is told each step as it ends.
- A result is kept beside its run's log, on the machine only, at most 100
  errors and 50 warnings, and is removed when the log is.

**`latem approve` asks for a person at a terminal** (A89). A held run is
approved by whoever is at the machine, and until now nothing checked that
anyone was: an agent that reaches `latem mcp` over ssh could run
`latem approve` the same way.

- Without a terminal on both stdin and stdout it refuses with exit `4`, before
  it reads anything. No flag skips it.
- At a terminal it shows the run, its commit and why it is held, and approves
  only when you type the start of that commit, 7 characters or more.
- It is a guard against an agent approving in the course of its work, not a
  wall against whoever holds the account. An agent that makes itself a
  terminal with `ssh -tt` still gets one.

### Upgrading from v0.8.0

- **Installed with `install.sh`:** run `latem update` once.
- **Installed with Homebrew:** run `brew upgrade latem`.

Either way, the running agent moves onto the new version at the first moment
no build is in flight.

**A script that ran `latem approve` now gets exit 4.** Approve at a terminal.
Over ssh, log in and run it at the prompt.

**A machine builds as it did until you ask for the rest.** No workspace is
kept unless a job says `workspace: warm`, and `latem mcp` takes no changes
unless a repository's config says `agent_changes = true`. Results are written
for every run, as one small file beside each log.

**The wire protocol is still 2.9**, so latem.dev and machines on v0.8.0 are
unaffected, and v0.9.0 leaves `state.db` as v0.8.0 left it.
