## What changed

**Workflow variables come from OpenVault too** (RUNNER_SPEC A96). With
`[secrets] openvault = true`, a job's `${{ vars.NAME }}` of repository `R` in
environment `E` is read from collection `R`: entry `E/NAME`, then `NAME`. In
each scope the vault comes before `config.toml`, the way secrets already work,
so a value set once reaches every machine that builds the repository. A new
machine no longer needs each variable copied into its config by hand, and
machines stop disagreeing about a value nobody meant to differ (A68).

```console
$ openvault set latem-cloud/LATEM --var <<<"true"
$ openvault set take-one/production/CLOUDFLARE_ACCOUNT_ID --var < id.txt
$ latem vars list --repo take-one
REPO      ENVIRONMENT  NAME                   VALUE   SOURCE
take-one  production   CLOUDFLARE_ACCOUNT_ID  …       openvault
```

- Only an entry of kind **variable** answers `vars.*`. A secret is masked in a
  log and a variable is not, so a secret never fills a variable, even one
  with the same name.
- The vault is asked only when an expression reads `vars`. A job that reads a
  variable while the OpenVault service is down fails with `E_SECRET_BACKEND`
  and is retried; it never runs with the variable empty or with the machine's
  stale copy. A job that reads no variable runs as before.
- The heartbeat refreshes its variable digests once a minute, and keeps the
  last ones through a service outage, so latem-cloud doesn't see the machine
  as different from its peers while the service restarts.

**`latem setup` checks OpenVault before it says `latem secrets set`**
(A97). The plan now names the step that closes each gap:

| Item | When | Whose |
|---|---|---|
| `openvault-on` | a vault here holds one of this machine's repositories, and the config doesn't read it | latem's: `setup apply` writes `[secrets] openvault = true` |
| `openvault-service` | the service doesn't answer | latem's: `setup apply` runs `openvault service install` |
| `openvault-join` | this device isn't in a vault | yours: `openvault join`, then approve it on a device in the vault |
| `openvault-collection-R` | this device has no collection for `R` | yours, on an admin device: `openvault scope <device> R read` |
| `secrets-R`, `vars-R` | a job reads a name the collection lacks | yours: `openvault set R/E/NAME --secret` or `--var` |

Without OpenVault installed, `latem secrets set` and `latem vars set` stay the
fix. Variables a job reads that no source holds now get an item of their own.
Everything that is yours exits `4` under `latem setup apply`, and `latem mcp`'s
`getReadiness` returns the same plan.

**A stopped OpenVault service is retried, as A86 always said.** A job that
needed a secret while the service was down failed with `E_MISSING_SECRET`,
which is never retried. It is now `E_SECRET_BACKEND`.

### Upgrading from v0.10.0

- **Installed with `install.sh`:** run `latem update` once.
- **Installed with Homebrew:** run `brew upgrade latem`.

The running agent moves onto the new version at the first moment no build is
in flight. Nothing changes for a machine without `[secrets] openvault = true`.
With it, variables you add to the vault take over from `config.toml`'s; until
you add any, every job reads what it read before. The wire protocol is still
2.9, latem-cloud needs no change, and `config.toml` and `state.db` are read as
v0.10.0 left them. v0.11.0 writes one new file, `~/.latem/openvault-vars.json`,
which holds variable digests and never a value.
