## What changed

**A pull request's job waits for you before it can reach this machine's
secrets** (RUNNER_SPEC A85). Until now, anyone who could open a pull request
could read every secret the machine held. `latem repo add` allows
`refs/pull/*/merge`, so the job built without approval, and it was compiled
from the pull request's own commit, so it could name any secret or
`environment:`.

A job whose ref is under `refs/pull/` now waits in `awaiting_approval`, before
any store is asked for anything, when:

- it asks for any of the machine's secrets; or
- it runs on a native runner, whether it asks for secrets or not, because a
  native step runs as the agent's user, beside every store.

A pull request's job that asks for no secret and runs on Docker builds as
before. Forks and pull requests from the same repository are held alike.

To let one through, on the machine that holds it:

```sh
latem list --state awaiting_approval
latem logs <run-id>       # its commit, and what it asks for
latem approve <run-id>    # after reading the commit
```

An approval covers that one commit. The next push is held again. A run nobody
approves is rejected after the repository's `approval_ttl`, 24 hours unless
set.

**Secrets can come from OpenVault, read when each job starts** (A86). With
`[secrets] openvault = true` in `config.toml`, a workflow job's secret of
repository `R` is read from OpenVault collection `R`: entry `E/NAME` for its
environment `E`, then `NAME`. The collection is named exactly as the
`[repos.<key>]` key, hyphens included.

- It is asked after the environment and before `secrets.env`, the Keychain,
  pass and commands.
- It is off until the config says so. A vault existing is not enough.
- latem talks to the service's local socket and never runs `openvault`. If the
  service doesn't answer, the job fails with `E_SECRET_BACKEND` rather than
  run without its secret. `openvault service install` keeps the service
  running across reboots.
- `latem secrets list` and `latem workflows check` count OpenVault's names.
  `latem doctor` says whether the service answers, and names each repository
  with no collection here.

**`latem mcp` lets an agent on another machine watch and drive the builds
here** (A87). It speaks the Model Context Protocol on stdin and stdout, so an
agent starts it over ssh and it listens on nothing:

```sh
claude mcp add --scope user mini -- ssh mini .local/bin/latem mcp
```

latem is named by its path because ssh runs a command with a short `PATH`,
which has neither `~/.local/bin`, where `install.sh` puts it, nor Homebrew's
bin. With Homebrew on a Mac with Apple silicon, use `/opt/homebrew/bin/latem`.

Its tools list runs, including every run of one commit, show one, read its
log, wait for it to finish, start a `.latem/jobs.yaml` job, cancel a run, and
check which of a repository's workflow jobs the machine can run. It never
approves: a run held for approval, by the rule above or by `allowed_refs`,
waits for a person at the machine. Secrets, vars, repositories, the service,
setup and update are not offered either.

### Upgrading from v0.6.0

- **Installed with `install.sh`:** run `latem update` once.
- **Installed with Homebrew:** run `brew upgrade latem`.

Either way, the running agent moves onto the new version at the first moment
no build is in flight.

**Every pull-request check that needs a secret, or runs on a native runner,
now waits for `latem approve` on every push.** That includes every iOS check
on a Mac.

**The wire protocol is still 2.9**, so latem.dev and machines on v0.6.0 are
unaffected. The first time v0.7.0 opens `state.db`, it adds one index to the
runs table, once.
