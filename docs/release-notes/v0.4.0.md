## What changed

**`latem try <job>` runs a workflow job before you push it** (RUNNER_SPEC A76).
It takes the checkout in front of you, uncommitted and untracked changes
included, and runs one job on this machine, on its runners, toolchains and
secrets:

```sh
latem try test
latem try -C ~/src/app --workflow checks.yml beacon
latem try deploy --event workflow_dispatch --input target=staging
latem try build --matrix os=ubuntu-latest
```

- It needs the agent running on this machine; it queues the job there and
  follows the log. Ctrl-C cancels the run, and `--detach` queues it and exits.
- Nothing is pushed, and nothing about the run reaches latem.dev. Your index,
  branches and stash are left as they were.
- The job runs as a push to your branch would run it, except that `on:` and
  the job's `if:` are not evaluated, and its `needs` count as succeeded with no
  outputs.
- The job gets no GitHub token. `GITHUB_TOKEN` is this machine's secret of that
  name if it has one (`latem secrets set --repo R GITHUB_TOKEN`), otherwise it
  is empty.
- A job this machine cannot run is refused with the fix, as
  `latem workflows check` reports it, before anything is queued.

**`ltm` is latem's short name** (A79): `ltm run myapp test`, `ltm doctor`,
`ltm try test`. It is a link to `latem` beside it, and `ltm --help` and
`ltm completion zsh` are written for the name you typed. `install.sh` adds it,
`latem update` from v0.4.0 on adds it on a machine that has none, and the
Homebrew formula installs it from this release on. A file called `ltm` that is not latem's is
left alone.

**More `upload-artifact` and `download-artifact` steps run** (A77):

- An artifact's `name:` and `path:` may read a step's outputs or
  `${{ runner.temp }}`. They are resolved as the step starts.
- A path may be in `runner.temp` as well as the workspace, on a native runner.
  On a docker runner, `runner.temp` is inside the container, so the step fails
  with `E_ARTIFACT` and says why.
- upload-artifact v7's `archive: false` uploads one file as it is, under its
  own name.

### Upgrading from v0.3.1

The wire protocol is still 2.7, so there is nothing to change on latem.dev, and
machines on v0.3.x and v0.4.0 can run side by side.

- **Installed with `install.sh`:** run `latem update` twice. The first run
  installs v0.4.0, and the agent moves onto it without cancelling a build. That
  run is still v0.3.x's code, which has no `ltm`, so it adds no link. The second
  run is v0.4.0's: it finds nothing newer to install and adds `ltm`. A machine
  that updated itself with `agent.auto_update` already has v0.4.0 and needs
  only the second run.
- **Installed with Homebrew:** run `brew upgrade latem`. The running agent
  moves onto the new version by itself at the first moment no build is in
  flight. The new formula adds `ltm` and its shell completions.

Two artifact changes can alter a job that ran before:

- **Artifacts are stored as GitHub stores them**, relative to the root
  upload-artifact gives them: `path: dist` stores `app.js`, not `dist/app.js`.
  A step that downloads an artifact uploaded earlier in the same job now finds
  its files where it would on GitHub. One written for latem's earlier layout
  finds them one directory higher.
- **A download that only another job could satisfy is refused when the job is
  planned**, naming A52, and `latem workflows check` reports it. Before, such a
  job was admitted and then failed at the step. Artifacts do not yet cross jobs
  on latem.

Coming from v0.3.0 or earlier, the v0.3.1 notes say how to move a machine to
Homebrew.

### Fixed

- A `strategy.matrix` larger than 256 jobs is refused before latem builds it,
  not after, so a very large matrix can no longer use a lot of memory on its
  way to the same error.
